PLATFORM ENGINEERING · EDITORIAL DRAFT

Building an Internal Developer Platform on AWS: Golden Paths, Terraform, and Kubernetes

A reference design for reducing delivery friction without giving every application team unrestricted cloud access.

Audience: Staff engineers, platform teams, cloud architects, and engineering leaders. Status: Illustrative architecture; not a claim of an implemented production platform. Editorial date: November 21, 2026.

The problem: too many decisions per deployment

A developer who wants to ship a small service may first need a repository, pipeline, cloud account access, DNS, container registry, secrets, runtime, dashboards, and a deployment process. Each request is individually reasonable; together they create a ticket-driven bottleneck. Teams then copy old configurations, create one-off automation, or bypass controls to move faster. The result is an inconsistent estate that becomes difficult to patch, observe, and recover.

An internal developer platform (IDP) is not merely a portal. It is a set of reusable capabilities and contracts that turns common engineering work into a supported product. The goal is to make the secure, observable, maintainable path the easiest path. Teams should retain meaningful application choices while the platform standardizes the expensive undifferentiated work.

Begin with a golden path, not a giant platform

Choose one workload archetype: for example, a stateless Java/Spring Boot HTTP service deployed to Amazon EKS. Interview application teams about their actual blockers. Define a first golden path that creates a repository, builds and scans an image, deploys to a nonproduction namespace, exposes telemetry, and offers a documented rollback. Measure time-to-first-deployment and support burden before expanding to scheduled jobs, event consumers, or stateful services.

A golden path should be opinionated but not compulsory. Document its supported versions, ownership, extension points, service-level objectives, and exception process. Without that contract, a template quickly becomes another unmaintained code sample.

Reference architecture and responsibility boundaries

Developer → Service catalog / self-service request
          → Template + reviewed repository
          → CI: test → scan → build → signed artifact
          → Container registry (Amazon ECR)
          → GitOps change / approved deployment
          → Amazon EKS workload
          → Logs, metrics, traces, SLO dashboard

Platform control plane:
  Identity federation → scoped roles
  Terraform modules → VPC, EKS, IAM, registries
  Policy checks → admission and CI guardrails
  Secrets manager → workload identity → runtime secrets

Keep the control plane separate from application delivery. The platform team owns shared cluster lifecycle, network boundaries, module interfaces, deployment controllers, and policy defaults. Application teams own source code, service behavior, resource sizing within quotas, and application-level SLOs. Security owns policy intent and exception review; platform engineers make enforcement usable.

On AWS, prefer temporary credentials through federation and workload identity rather than static cloud keys. Use separate AWS accounts or other explicit trust boundaries for environments with different risk profiles. Treat the catalog as an inventory and workflow entry point, not the source of truth for IAM authorization.

Terraform modules as versioned platform APIs

Terraform is valuable when it exposes stable interfaces instead of handing every team unrestricted provider configuration. A platform module might create a service namespace, constrained IAM role, ECR repository, and approved monitoring integration. Consumers provide a small number of reviewed inputs. The module pins its provider compatibility, documents outputs, and has a semantic version and migration guide.

module "service_foundation" {
  source  = "git::https://example.invalid/platform-modules.git//service?ref=v1.0.0"
  service = "orders-api"
  env     = "dev"
  owner   = "payments-platform"
}

Illustrative only: the example URL is a placeholder, not a real dependency or deployable module. In production, reference an approved internal registry or immutable source revision. Store Terraform state remotely with access controls and locking where supported. Validate plans in CI; require approvals for changes that alter IAM, networking, data retention, or production infrastructure. Do not grant pull-request workflows broad apply permissions.

Separate provisioning from application deployment

A common failure is coupling cluster changes, IAM provisioning, and application releases into one opaque pipeline. Instead, treat infrastructure provisioning as a reviewed lifecycle with its own plan and approval gates. Treat application delivery as a repeatable process with unit tests, dependency and image scanning, provenance, and deployment promotion. GitOps can reconcile declared Kubernetes manifests, but it does not remove the need for authorization, drift detection, or rollback design.

For a Spring Boot workload, define readiness and liveness endpoints deliberately. Readiness should reflect whether the service can serve traffic; liveness should not restart healthy pods merely because a remote database is temporarily unavailable. Set CPU and memory requests from observed behavior, apply namespace quotas, and use PodDisruptionBudgets and topology spreading where availability requirements justify them.

Security guardrails that preserve developer flow

Security should be built into the template and pipeline rather than added as a late review. Start with least-privilege IAM, short-lived credentials, protected branches, dependency scanning, secret scanning, and signed or attestable artifacts. Restrict outbound network access where practical. Use Kubernetes RBAC and admission policies to reject privileged containers, unapproved registries, and missing resource constraints. Make policy errors actionable: explain what failed and show a compliant example.

Do not automatically elevate permissions to make a deployment pass. Provide an exception workflow with an owner, expiry, compensating controls, and an audit trail. Track time-to-remediation and exception volume; a rising exception count may indicate a platform design problem rather than developer resistance.

Reliability is part of the product

A platform is useful only if developers can trust it. Define SLOs for onboarding success, deployment workflow availability, and time to restore a failed deployment. Instrument CI durations, deployment failures, controller reconciliation errors, and cluster saturation. Connect each generated service to logs, metrics, traces, alerts, and a runbook from day one. Alert on symptoms that matter to users, not simply every infrastructure fluctuation.

Design rollback as a first-class operation: immutable image tags, versioned manifests, and a clear database migration strategy. A Kubernetes rollback does not reverse a destructive schema migration. Require compatibility planning for data changes, and rehearse recovery before claiming a workload is production-ready.

Measure adoption and developer outcomes

A portal's login count is not a platform success metric. Track onboarding lead time, deployment frequency, failed-change rate, time to restore service, and developer satisfaction. Segment results by service type and team maturity. Avoid optimizing a single metric at the expense of security or quality. For example, a fast deployment that regularly requires emergency manual repair is not a successful golden path.

Start with a small pilot cohort, record friction points, and improve the contract based on observed usage. Publish a service catalog entry with clear ownership and support expectations. Treat every breaking module upgrade like an API change: communicate early, offer migration tooling, and maintain a support window.

Practical implementation sequence

  1. Interview two or three application teams and select one common deployment workflow.
  2. Document the golden path's inputs, outputs, ownership, support boundaries, and success criteria.
  3. Build a versioned Terraform foundation module and validate plans without applying to production.
  4. Create a service template with tests, container build, dependency checks, and runtime configuration.
  5. Wire up reviewed deployment promotion and a rollback path.
  6. Add default dashboards, runbooks, and SLO instrumentation.
  7. Pilot with real users, measure time saved, and revise the workflow before scaling.

Trade-offs and decisions

Shared versus dedicated clusters: shared clusters improve utilization but increase multitenancy complexity; dedicated environments strengthen isolation at greater operational cost. Centralized versus federated platform ownership: a central team can enforce consistency, while embedded platform champions improve adoption. Portal versus API-first workflows: a portal improves discoverability, but stable APIs and Git-based workflows are essential for automation and accessibility. Opinionation versus flexibility: standardize the common path while publishing supported escape hatches.

The strongest platform engineering strategy is incremental. Deliver one trustworthy path, measure its effect, and extend it only when the next use case is understood. A platform that reduces cognitive load, preserves engineering autonomy, and makes operational quality visible is more valuable than a catalog of templates that nobody maintains.
